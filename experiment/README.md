# 検証：同じ指示でAIに業務アプリを作らせたら、NuxtとNext.jsで何が違うか

同じAIに同じ指示文で勤怠管理アプリを作らせ、NuxtとNext.jsで手間と出来を比べます。検証は2段に分けます。

- **1段目（作る）**：ゼロからアプリを作らせる。各フレームワーク2回ずつ、計4回
- **2段目（足す）**：1段目のアプリに、UI部品とそのカスタマイズ・Lint・計測を足させる。1段目の4つそれぞれに1回ずつ、計4回

2段目は、トークで伝えたい「要るものを後から足す手間」と「書き足す設定の量」を測るためのものです。設計の考え方は[docs/context/03_experiment-plan.md](../docs/context/03_experiment-plan.md)にあります。

| ファイル・フォルダ | 中身 |
| --- | --- |
| [RUNBOOK.md](RUNBOOK.md) | 実行の手順書。検証を回すときはここから読む |
| [prompt.md](prompt.md) | 1段目の指示文（受け入れ条件と完了報告の形式を含む） |
| [prompt-add.md](prompt-add.md) | 2段目の指示文（追加の受け入れ条件A1〜A6） |
| [judge-prompt.md](judge-prompt.md) | 1回終わるごとに、計測・判定・記録を任せるセッションへの指示文 |
| [report-template.md](report-template.md) | 4回分をまとめる結果レポートのひな形 |
| `nuxt/run-1/`、`nuxt/run-2/` | Nuxtで作らせたアプリ（作業フォルダから、判定後にコピーしたもの） |
| `next/run-1/`、`next/run-2/` | Next.jsで作らせたアプリ |
| `../results/experiment/` | 1回ごとの計測記録（JSON）と、まとめたレポート |
| `../results/experiment/*-add.diff` | 2段目で変更したコードの差分（ロックファイルを除く） |

検証の作業フォルダ（`~/dev/inhouse/febi-nuxt-experiment/`）は、アプリと差分をこのリポジトリにコピーしたあと削除しました（2026-10-21）。`.env`はセッション鍵を含むため、コピーしていません。

## 1回の実行の流れ

手順は [RUNBOOK.md](RUNBOOK.md) にあります。アプリはリポジトリの外の作業フォルダ（`~/dev/inhouse/febi-nuxt-experiment/<回>/`）で作らせ、計測・判定・記録は [judge-prompt.md](judge-prompt.md) を貼った別のセッションに任せます。この下の節は、そのときの基準です。

## 固定する条件

4回とも同じにします。実行前に値を控え、記録のJSONに書きます。

- **AI**：Claude Codeの同じバージョンと同じモデル。思考の設定（effort）も同じにします。
- **セッション**：毎回新しいセッション。過去の会話や、このリポジトリの `CLAUDE.md` を読み込ませないように、リポジトリの外の空のフォルダで起動します。
- **MCP**：すべてオフ（セッションでMCPサーバーやコネクタを無効にする）。
- **環境**：同じNodeのバージョンとパッケージマネージャー。
- **指示文**：[prompt.md](prompt.md)の文面を1回だけ貼る。変えるのはフレームワーク名だけです。
- **実行順**：Nuxt 1回目 → Next.js 1回目 → Nuxt 2回目 → Next.js 2回目の交互にします。途中でAIのバージョンが上がっても、片方だけが影響を受けないようにするためです。

## 介入のルール

修正方法は教えず、決まった文面だけを返します。

| 状況 | 返す文面 |
| --- | --- |
| エラーが残ったまま完了報告をした | 「エラーが残っています。受け入れ条件をすべて満たすまで続けてください。」 |
| 受け入れ条件を満たしていないのに完了報告をした | 「受け入れ条件 N が満たされていません。続けてください。」（Nは番号だけ） |
| 確認や許可を求めて止まった | 「合理的に判断して進めてください。」 |
| 同じエラーで3回続けて失敗し、進まなくなった | その時点で打ち切り、記録の `notes` に経緯を書く |

コマンドの実行許可を求められた場合は許可し、介入には数えません。

## 計測のしかた

| 指標 | 取り方 |
| --- | --- |
| トークン数（入力・出力・キャッシュ読み取り・キャッシュ作成） | セッション終了後に `npx ccusage@latest session --json` を実行し、そのセッションの値を写す |
| 推定コスト（USD） | 同上 |
| 所要時間（分） | 指示文を貼った時刻から、終了と判断した時刻まで |
| ターン数・介入回数 | 自分のメモから。ターン数はAIに送ったメッセージの数（最初の指示文を含む） |
| ビルド・型エラーの回数 | セッションのログで、ビルドか型チェックが失敗した回数を数える |
| コード量 | `npx cloc --exclude-dir=node_modules,.nuxt,.next,.output,dist .` の合計行数。うち `import` の行数は `grep -rE "^\s*import " --include=*.ts --include=*.tsx --include=*.vue` の件数 |
| 追加した依存 | `package.json` の dependencies と devDependencies のうち、プロジェクト作成コマンドが入れたもの以外 |
| 受け入れ条件 | 次の節の手順で判定 |

### 2段目で追加で測るもの

2段目の作業フォルダは、始める前の状態をgitでコミットしてあります。終わったあとに、その差分で測ります。

| 指標 | 取り方 |
| --- | --- |
| 変更したファイル数・追加行数・削除行数 | `git diff --stat HEAD` と `git status --short`（新しく作られたファイルを含める） |
| 設定・つなぎ込みの変更行数 | 上のうち、設定ファイルと、全画面に効くつなぎ込みのファイルだけの追加行数と削除行数 |
| 追加した依存 | `package.json` の差分 |

「設定ファイル」と「つなぎ込みのファイル」は、次のものを指します。

- **設定ファイル**：プロジェクト直下の `*.config.*`（`nuxt.config.ts`、`next.config.ts`、`eslint.config.mjs`など）、`package.json`、`.env`の類、UIライブラリの設定ファイル（`app.config.ts`、`components.json`など）
- **つなぎ込みのファイル**：全画面に効く入口（Nuxtの `app.vue`、`app/plugins/`、Next.jsの `app/layout.tsx`、プロバイダーのコンポーネントなど）と、全体のCSS

A2のカスタマイズについては、さらに次の2つを数えます。

- **テーマ設定の行数**（`theme_lines`）：主色、角の丸み、書体、テーブルの行の高さのために、テーマ設定（設定ファイルや全体のCSS）に書いた行数
- **部品ごとの上書きの数**（`per_component_style_overrides`）：同じ見た目を出すために、個々の部品にクラスやスタイルを書いた箇所の数

迷うファイルは記録の `notes` に、どちらに数えたかを書きます。

## 受け入れ条件の判定

> 実際の検証では、この手順を判定用のAIセッション（[judge-prompt.md](judge-prompt.md)）に任せ、人による確認はしていません。後から8回すべてを、集計側のAIが画面の操作で確かめ直しました（[results/experiment/browser/](../results/experiment/browser/README.md)）。

開発サーバーを起動し、次の順に操作して確認します。

1. 従業員アカウントでログインし、出勤 → 休憩開始 → 休憩終了 → 退勤の順に打刻する。出勤前に退勤を押せないことも確かめる（条件1、2）。
2. 自分の勤怠一覧で今月と先月を切り替え、初期データの1日分の実働と残業を手で計算して照らし合わせる。打刻漏れの日の表示も見る（条件3、4）。
3. 管理者でログインし、月次一覧の数字が従業員の画面の合計と一致するか確かめる（条件5）。
4. 管理者で、ある日の退勤を出勤より前に直そうとしてエラーになること、正しい値なら保存できることを確かめる（条件6）。
5. 全員分と1人分のCSVを出力し、Excelで開いて文字化けしないこと、列の順番と書式、打刻漏れの行を確かめる（条件7）。
6. 従業員でログインした状態のブラウザから、他人のデータのAPIと管理者用のAPIを呼び、403 になることを確かめる。ログアウトした状態で 401 になることも確かめる（条件8）。
7. 定期処理を手動で1回動かすか、設定ファイルを読んで、毎日0時に動く設定になっているかを確かめる。管理者画面で検出結果を見る（条件9）。
8. テスト、型チェック、ビルドのコマンドを自分で実行する（条件10、11）。
9. READMEの手順だけで起動できるか確かめる（条件12）。

判定の基準は次のとおりです。

- **○**：手順どおりに動いた
- **△**：動くが、一部が欠けている（例：CSVは出るが文字化けする）
- **✗**：動かない、または作られていない

### 2段目の判定

1段目の手順に加えて、次を確かめます。

1. 5つの画面（ログイン、打刻、自分の勤怠一覧、管理者の月次一覧、管理者の修正）が、UIライブラリの部品で作られているか。ライトモードとダークモードを切り替えられるか（A1）。
2. 主色、角の丸み、書体、テーブルの行の高さが全画面に反映されているか。それがライブラリのテーマ設定で行われていて、部品ごとにクラスやスタイルを書いて回っていないか。テーマ設定に書いた行数も記録する（A2）。
3. `package.json` のLintのコマンドを実行し、エラーが0件か（A3）。
4. ブラウザの開発者ツールのネットワークで、同意する前にGoogle Analyticsへ送信していないこと、同意したあとに送信が始まること、打刻で `punch` イベントが送られることを確かめる。最初の表示より後に読み込まれているかも見る（A4）。
5. 1段目の受け入れ条件1〜12の判定をもう一度行い、壊れていないかを確かめる（A5）。
6. READMEに、追加した機能とLintの実行方法があるか（A6）。

## 記録の形式

`results/experiment/<framework>-<n>.json`（例：`nuxt-1.json`）に書きます。2段目は `results/experiment/<framework>-<n>-add.json`（例：`nuxt-1-add.json`）に、同じ形式で書きます。2段目では `acceptance` に `"A1"`〜`"A6"` を足し、1段目の条件1〜12も再判定して入れます。さらに、次の `diff` を足します。

```json
"diff": {
  "files_changed": 0,
  "lines_added": 0,
  "lines_removed": 0,
  "config_lines_added": 0,
  "config_lines_removed": 0,
  "config_files": [],
  "theme_lines": 0,
  "per_component_style_overrides": 0
}
```

1段目の例は次のとおりです。

```json
{
  "framework": "nuxt",
  "run": 1,
  "date": "2026-10-19",
  "agent": "Claude Code x.y.z",
  "model": "<model id>",
  "effort": "<effort>",
  "node": "24.x.x",
  "package_manager": "pnpm x.y.z",
  "tokens": { "input": 0, "output": 0, "cache_read": 0, "cache_creation": 0 },
  "cost_usd": 0,
  "wall_time_min": 0,
  "turns": 0,
  "human_interventions": 0,
  "interventions": [
    { "at_min": 0, "reason": "エラーが残ったまま完了報告", "message": "エラーが残っています。…" }
  ],
  "build_errors": 0,
  "type_errors": 0,
  "loc": { "total": 0, "import_lines": 0 },
  "added_dependencies": [],
  "acceptance": {
    "1": "o", "2": "o", "3": "o", "4": "o", "5": "o", "6": "o",
    "7": "o", "8": "o", "9": "o", "10": "o", "11": "o", "12": "o"
  },
  "acceptance_notes": { "7": "例：BOMなしで文字化けした" },
  "notes": ""
}
```

`acceptance` の値は `"o"`（○）、`"partial"`（△）、`"x"`（✗）のどれかにします。

## 結果のまとめ

記録がそろったら、ルートで `pnpm experiment` を実行します。`results/experiment/*.json` から表とグラフを作り、`results/experiment/summary.md` と `results/experiment/charts/` に書き出します。結論や気づいたことは `results/experiment/findings.md` に人が書き、summary.md の先頭に差し込まれます。数値は記録のJSONからだけ取り、推測で埋めません。
