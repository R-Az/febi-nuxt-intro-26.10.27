## 判断したこと

- **毎日0時の処理は2通り用意しました。** 常駐サーバーでは `instrumentation.ts` がタイマーを登録し、日本時間の0時に動かします。データがメモリにあるので、こちらが基本です。サーバーレス向けには `vercel.json` の Cron（15:00 UTC）から `/api/cron/detect-missing-clock-outs` を呼ぶ設定も入れました。Next.js 自体には定期実行の機能がないためです。
- **画面はクライアント側から API を fetch する作りにしました。** 「画面から直接データを読まない」を確実に守るためです。
- **ログイン状態は署名付き Cookie で持ちます。** 有効期限は12時間で、`proxy.ts` と API の両方で検証します。
- **退勤のない当日分は「打刻漏れ」ではなく「勤務中」と表示します。** 打刻漏れの件数にも数えません。CSV の備考は「勤務中」になります。
- 休憩は1日に何回でも取れます。休憩中は退勤できません。
- 管理者は打刻しない役割にしました。月次一覧などの対象も従業員4人だけです。
- **初期データについて**
  - 打刻を試せるように、今日の分は空けてあります。
  - 打刻漏れの検出記録も2件入れてあります（定期処理がこれまで動いていた想定）。
- **管理者の修正について**
  - 出勤・退勤・休憩をすべて空にすると、その日の勤怠を削除します。
  - 退勤を空にしたまま保存すると、打刻漏れのまま残ります。
  - 未来の日付は修正できません。
- **CSV について**
  - 出勤の記録がある日だけを出力します。
  - 日別の一覧画面には、記録がない日も含めて月の全日を表示します。
- 打刻漏れ画面には、取りこぼしに備えて日付を指定する「手動で検出」ボタンと、修正済みかどうかの表示を付けました。

## 残っている問題

- 日をまたぐ勤務（深夜0時以降の退勤）には対応していません。
- 祝日を考慮していません。初期データは土日だけを除いています。
- 0時にサーバーが止まっていると、その日の検出は自動では再実行されません（手動で検出できます）。
- サーバーレス環境ではメモリ上のデータが共有されないため、Vercel Cron の設定は実際のデータベースを使う前提でしか意味がありません。
- **セキュリティについて**
  - ログアウトは Cookie を消すだけです。盗まれたトークンは期限まで使えてしまいます。
  - ログイン試行の回数制限はありません。
- 月をまたぐ瞬間に画面を開くと、サーバーとブラウザで初期表示の月がずれる可能性があります（表示上の警告だけです）。
- `npm audit` が、`create-next-app` の初期構成に対して high を5件報告しています。中身は調べていません。
- 画面の自動テスト（E2E）は書いていません。画面の確認は手作業です。
- **試した操作のデータが残っています。** 開発サーバーは動いたままで、試しに打刻した勤怠（E001 / E002 / E003 の今日分）と、修正した勤怠（E001 の 10/1、E004 の 10/16）がメモリに入っています。再起動すれば初期データに戻ります。
