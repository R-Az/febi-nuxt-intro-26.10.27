# チェックリスト

## 内容のレビュー

発表の前に、このリストに沿ってデッキをレビューしてもらいます：執筆に関わっていない同僚に頼むか、`/review`（事実確認も行う独立したAIレビュアー）を使います。レビュアーには、下書きの経緯ではなく、トークのピッチと構成を渡してください（`CLAUDE.local.md`はgit管理外なので、「ピッチ」と「構成」の部分をレビュー依頼に貼り付けます）。

**トーク全体**
- [ ] すべてのセクションがピッチと要点に役立っている。「面白いから」というだけで入っているものはない
- [ ] どの「どうやって」の前にも「なぜ」がある。スライド間で抜けているステップがない
- [ ] 導入で、最初の数分のうちに聴衆が関心を持つ理由を示している
- [ ] 振り返りと要点が、各セクションで実際に示した内容と一致している
- [ ] デモとクリックのステップも含めて50分に収まる

**ジュニアテスト**
- [ ] 説明する前に使っている用語、API、概念がない
- [ ] そのテーマをすでに知っている人にしかわからないスライドがない

**原則**（`PRINCIPLES.md`）
- [ ] **語るより見せる**：文章の多いスライドはデモ（振る舞い）か図（構造）にする。どのデモにも存在する理由がある
- [ ] **単体で伝わる**：どのスライドも発表者の話なしで成り立つ。発表者ノートや`<Spoiler>`の中にしかない結論はない
- [ ] **簡潔に、でも漏れなく**：1行の箇条書きは最大5つ程度。ただし本質的なものは削っていない
- [ ] **コード**：1ブロック12〜15行程度まで、焦点がはっきりしている。デモの横のコードは、そのデモが見せている結果を実際に生み出す
- [ ] **クリック**：順序に意味があるとき、スライドの情報量が多いとき、結論を先に見せたくないときだけ使っている
- [ ] **読みやすさ**：後ろの席から読める文字の大きさ。十分なコントラスト。正誤や状態を色だけで伝えていない
- [ ] **公開しても安全**：クライアント名やプロジェクト名、社内URL、社内のスクリーンショット、認証情報、個人情報がない

**事実**（最も重要な部分）
- [ ] 事実に関する主張（振る舞い、APIの意味、数値、パフォーマンス、ブラウザ対応、引用、日付、歴史）をすべて書き出し、それぞれを一次情報で確認している：MDN、仕様（WHATWG、W3C、TC39、CSSWG）、公式ドキュメント、web.dev / Chrome docs、caniuse / Baselineのデータ
- [ ] 引用した出典が、その主張を実際に述べている（ラベルを信用せず、開いて確認する）。リンクが正しいページを開く（MDNの`/ja/`は翻訳がないと404になる）
- [ ] ブラウザ対応のデータが最新で、日付（`as-of`）があり、対象の機能名を示している
- [ ] コード例が動き、スライドの説明どおりに動作する

**言語**
- [ ] 日本語が自然に読める（です/ます調、em-dashなし、用語が統一されている）
- [ ] 第二言語デッキがスライド単位で対応しており、直訳ではなく聴衆に合わせた調整として読める

**想定される質問**：ジュニアやシニアがおそらく尋ねる質問を5〜8個書き出し、デッキがすでにそれに答えているか確認します。

## 発表当日

まず`pnpm check`を実行し（すべてのデッキをビルドし、`pnpm preflight`を実行します）、それから：

- [ ] デプロイしたURLが開け、最後のデプロイが成功している（GitHub → Actions）
- [ ] 発表者モード（`/presenter`）がセカンドスクリーンで動く。使う場合はノートが表示される
- [ ] デモの操作ボタンをクリックした後や、デモの入力欄に入力した後でも、クリッカー／矢印キーでスライドが進む（先に入力欄の外をクリックする）
- [ ] ネットワークやサーバーが必要なデモが、会場のネットワークで動く
- [ ] DevToolsのデモ：ブラウザのウィンドウとタブを準備済み（パネルを開いておく、必要ならCPUスロットリングの準備）
- [ ] ブラウザのズームが100%、通知がオフ、私的なタブやブックマークが画面に映らない
- [ ] デッキをファイルで共有する場合は、PDFをエクスポート済み（`pnpm export`）
