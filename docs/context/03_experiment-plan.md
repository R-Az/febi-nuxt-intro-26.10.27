# 03. 検証企画:同じ指示で AI に業務アプリを作らせたら、Nuxt と Next.js で何が違うか

> 2026-10-19 追記: 1 段目(作る)のあとに、2 段目(足す)を加えた。1 段目のアプリに、同じ文面で UI 部品とそのカスタマイズ・Lint・計測を足させ、追加の手間と書き足した設定の量を測る。1 段目の題材では、トークで推したい「後から足す」「設定が少ない」が測れなかったため。指示文は `experiment/prompt-add.md`。
>
> 2026-10-15 改訂: 題材を「勉強会の告知サイト」から「小さな会社向けの勤怠管理アプリ」に変え、回数を「2 ラウンド × 各 3 回」から「1 条件 × 各 2 回(計 4 回)」に減らした。実行の手順・指示文・記録の形式は `experiment/` にある。

## 1. 問い

> 同じ AI・同じ指示で同じ業務アプリを作らせたとき、Nuxt と Next.js で
> **トークン消費量・所要時間・人の介入回数・完成度** はどう違うか?

## 2. 題材を業務アプリにした理由

聴衆が実際に作るのは、告知サイトより社内・取引先向けの業務アプリ(B2B)の方が多い。業務アプリでは SEO や広告計測より、ログイン・権限・API・帳票出力が中心になる。題材をそちらに寄せた方が、「Nuxt なら業務アプリもサクッと作れるか」という問いに正面から答えられる。

題材は **小さな会社(従業員 10〜30 人)向けの勤怠管理アプリ** にした。打刻・勤怠一覧・管理者の修正・CSV 出力という、業務アプリでよくある機能が一通り入り、1 時間前後で作れる規模に収まる。DB はモック(サーバー側のメモリ)にして、環境構築の差が結果に混ざらないようにする。

受け入れ条件は 12 項目(`experiment/prompt.md`)。主なものはログイン、打刻、勤怠の計算ルール、管理者の月次一覧と修正、CSV 出力(列と文字コードまで指定)、API の権限チェック(401 / 403)、毎日 0 時の定期処理、計算ロジックの単体テスト。

## 3. 仮説(事前に宣言しておく)

- **H1**: Nuxt は自動インポートと規約により、**出力トークンとコード行数が少ない**。
- **H2**: Nuxt は API(Nitro の `server/api`)と画面を同じ規約で書け、定期処理も Nitro Tasks で書けるので、**手戻りと追加依存が少ない**。
- **H3(反証候補)**: 学習データの量の差で、**Next.js の方がエラーや介入が少ない** 可能性もある(Web-Bench の結果)。

どの結果でも発表が成り立つようにする。「Nuxt が楽だった」でも「AI だと Next.js の方が楽だった。ただし出来上がるコードは Nuxt の方が短い」でも話になる(`04` のストーリー分岐)。

## 4. 実験条件

| 項目 | 内容 |
| --- | --- |
| 条件 | 1 つだけ。公式・定番のモジュールやライブラリを自由に使ってよい(旧計画の R2 に当たる) |
| 回数 | 1 段目:Nuxt 2 回、Next.js 2 回(交互に実行)。2 段目:1 段目の 4 つのアプリそれぞれに 1 回ずつ |
| 固定するもの | AI のバージョン・モデル・effort、毎回新しいセッション、空のフォルダ、MCP オフ、CLAUDE.md なし、Node とパッケージマネージャーのバージョン、指示文(フレームワーク名以外は同じ) |
| 介入 | 修正方法は教えず、決まった文面だけを返す(`experiment/README.md` の「介入のルール」) |

旧計画の R1(追加ライブラリなし)と R3(自作テンプレートから開始)はやらない。R1 がないので「本体の差より、エコシステムの差が効く」という比較はできない。

## 5. 計測指標

| 指標 | 意味 |
| --- | --- |
| 出力トークン・コード行数(うち import 行) | 書く量の少なさ |
| 入力・キャッシュのトークン | AI がどれだけファイルやドキュメントを読み回ったか |
| 推定コスト | 上の合計 |
| 所要時間・ターン数・介入回数 | 人の手間 |
| ビルド・型エラーの回数 | 手戻りの多さ |
| 追加した依存 | エコシステムの使われ方 |
| (2 段目)変更したファイル数・行数、うち設定とつなぎ込みの行数 | 後から足すときの手間と、設定の少なさ |
| 受け入れ条件の達成数(12 件中) | 出来。AI の自己申告ではなく、手で動かして判定する |

取り方と判定の手順は `experiment/README.md` にある。旧計画にあった Lighthouse(SEO・Performance)は、業務アプリでは比べる意味が薄いので外した。

## 6. 結果の記録とまとめ

- 1 回ごとの記録: `results/experiment/<framework>-<n>.json`
- AI の完了報告: `results/experiment/<framework>-<n>-report.md`
- 4 回分のまとめ: `results/experiment/summary.md`(ひな形は `experiment/report-template.md`)

## 7. 公平性・限界(発表で必ず明示)

- 各 2 回なので、「傾向」であって統計的な結論ではない。1 回目と 2 回目の値も並べて、ぶれの大きさを見せる。
- 単一モデル・単一エージェントの結果。モデルが変われば変わる。
- 学習データ量の差(Next.js の方が多い)は条件として制御できない。むしろそれ込みの「現実の使い心地」を測っている。
- 指示文にはフレームワーク固有の用語やライブラリ名を入れない(「API を用意する」とだけ書き、`server/api` や `route.ts` とは書かない)。

## 8. 進め方(目安)

1. 固定条件を決めて控える(半日)
2. 4 回実行する(1 回 30〜60 分。判定と記録を含めて平日 1 日強)
3. 集計とグラフ化(半日)
4. 発表資料に反映(結果がどう出ても `04` のストーリー分岐を使う)
